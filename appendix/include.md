## Программа в виде проекта

В курсе мы писали маленькие программы в одном файле. Когда программа была больше 100 строк, было неудобно искать информацию о нужной функции.  Хотелось разбить программу на несколько файлов. Например, реализацию стека написать в одном файле, а калькулятор с его использованием - в другом.

Когда пишут "настоящие программы", проект может быть в нескольких тысячах файлов. Общий код разбивают на отдельные файлы, раскладывают их по директориям, то есть организуют в **модули**. Файлы обращаются друг к другу через вызовы функций - фиксированное API. Стараются сделать меньше связей между модулями.

* **Черный ящик**. Используют модуль через его API. Не задумываются о его реализации. Один программист реализует функции для работы со стеком. Другой смотрит на прототипы этих функций и пишет калькулятор. Второй программист может не знать как именно реализовали стек: на основе динамического массива или односвязного списка. Каждая команда отвечает за свой модуль. Программисты одной команды работают  над своими модулями и только используют чужие.

* **Легче искать ошибку и организовывать код**. Разложим код по файлам и по папкам, как вещи в шкафу. Удобнее искать носки в одном ящике, чем перерывать все полки. Можно отдельно отладить и проверить функции работы со стеком. Если в калькуляторе хорошо работает сложение, но плохо вычитание, то проблема не в функциях работы со стеком, а в реализации алгоритма вычитания.

* **Замена модуля**. Если у нас список на основе массива из 20 элементов и его не хватает, мы можем переписать только функции реализации стека на динамический массив или список. Не трогая логику калькулятора.

Разделили программу на несколько файлов. Как использовать из другого файла

* функцию;
* переменную;
* макрос;
* структуру и typedef?

Как скомпилировать и собрать много `.c` в один исполняемый файл?

### Компиляция и сборка проекта

Если программа состоит из файлов `a.c` и `b.c`, а исполняемый модуль `hello.exe`, то для компиляции и сборки нужных `.c` просто перечислите их:

```cpp
gcc -Wall -Wextra -g a.c b.c -o hello.exe
```
Для ленивых, компиляция всех `.c` файлов в текущей директории, сборка в исполняемый модуль по умолчанию (`a.exe` или `a.out`):
```cpp
gcc -Wall -Wextra -g *.c
```
Для любознательных: используйте [make-файл](https://stepik.org/lesson/512586?unit=504796). О нем лучше прочитать в конце этого урока, когда вы поймете, что такое `.h` файлы и зачем они нужны.

Можно разделить компиляцию в объектные файлы `a.o` и `b.o` и их сборку в исполняемый модуль `hello.exe`:

* `gcc -c a.c` - скомпилировали файл `a.c` в объектный файл `a.o`.
* `gcc -c b.c` - скомпилировали файл `b.c` в объектный файл `b.o`.
* `gcc a.o b.o -o hello.exe` - собрали объектные файлы `a.o` и `b.o` в исполняемый модуль `hello.exe`.

## Вызов функции из другого файла

Самый простой случай. Напишите **прототип функции** в том файле, где вызываете функцию.

В файле `a.c` реализуем функцию `foo`, в файлах `a.c` и `b.c` используем её. 

```cpp
// Файл a.c`
#include <stdio.h>

void foo(int x);    // прототип функции

void bzz()
{
    foo(17);        // вызов функции, без прототипа foo работать не будет
}

void foo(int x)     // реализация функции
{
    printf("a.c foo: x=%d\n", x);
}
```
Другой файл:
```cpp
// Файл b.c

void foo(int x);    // прототип функции из другого файла

int main()
{
    foo(7);         // вызов функции из другого файла
    return 0;
}
```

### Ошибок нет

Прототип функции - это информация для компилятора. Обещание, что если мы вызовем функцию, то она где-то будет реализована.

Если указанная в прототипе функция нигде не реализована и не вызывается, то ошибки не будет.

Функция `not_implemented_yet_function` не вызывается. Все равно, реализована она или нет, ошибки не будет.

```cpp
// Файл b.c

void foo(int x);    // прототип функции из другого файла
void not_implemented_yet_function();    // только прототип

int main()
{
    foo(7);         // вызов функции из другого файла
    return 0;
}
```

### Ошибка компиляции

Если функция вызвана, а прототип её неизвестен, то будет ошибка компиляции. Вы это встречали раньше, когда опечатывались в названии функции. 

### Ошибка сборки

Если вызвана функция, которая нигде не реализована, то будет ошибка сборки.

```cpp
// Файл b.c

void foo(int x);            // прототип функции из другого файла
void unknown_function();    // прототип написан, функция нигде не реализована

int main()
{
    foo(7);                 // вызов функции из другого файла 
    unknown_function();     // вызов не реализованной функции
    
    return 0;
}
```
Скомпилируется файл без проблем: `gcc -c b.c` и будет создан файл `b.o`.

Но при сборке возникнет ошибка, что функция `unknown_function` не найдена.

```
gcc -o hello.exe a.o b.o
/usr/bin/ld: b.o: in function `main':
b.c:(.text+0x18): undefined reference to `unknown_function'
collect2: error: ld returned 1 exit status
```

## include

Большие проекты не пишутся один раз и больше не изменяются. Дописываются новые фичи, исправляются баги. Код меняется.

Допустим, в большом проекте мы написали функцию и используем ее во многих файлах. В этих файлах написаны её прототипы. Если мы хотим изменить тип параметра или возвращаемого значения, то надо изменить в реализации функции и найти везде, где она используется и в этих файлах поменять прототипы. Неудобно, большой шанс пропустить какой-нибудь файл. Хочется исправить в двух местах: в реализации и в описании прототипа. Чтобы в остальных местах исправилось само.

Такая функциональность есть. Можно написать все нужные прототипы функций в отдельном файле и вставить его во все нужные места с помощью команды препроцессора **include**. Она заменяет строку с именем файла на содержимое этого файла.

Файл называется **заголовочным** и принято, чтобы его расширение было `.h` (от header file).

Изменим пример, к файлам `a.c` и `b.c` добавится файл `a.h`.

### Создаем заголовочный файл `a.h`

```cpp
// Файл a.h

void foo(int x);
```
### Вставляем заголовочный файл в файл с реализацией функции

Добавили в файл с реализацией функции

```cpp
// Файл a.c`
#include <stdio.h>
#include "a.h"      // вставляем файл с прототипом функции

void bzz()
{
    foo(17);        // вызов функции, без прототипа foo работать не будет
}

void foo(int x)     // реализация функции
{
    printf("a.c foo: x=%d\n", x);
}
```
### Вставляем заголовочный файл в файл с вызовом функции

```cpp
// Файл b.c

#include "a.h"      // вставляем файл с прототипом функции

int main()
{
    foo(7);         // вызов функции из другого файла
    return 0;
}
```
В файле `stdio.h` описаны прототипы функций `scanf` и `printf`. Для того, чтобы вызывать эти функции, мы вставляем файл с их прототипами.

### `<>` и `""` в include

Обратите внимание, как вставили файл `stdio.h` и `a.h`. 

```cpp
#include <stdio.h>
#include "a.h"
```
Разница между `<>` и `""` в том, где будут искать указанные файлы.

* `#include <stdio.h>` ищет файл `stdio.h` в:
    * include-директориях, которые заданы как ключи компиляции в `gcc` или в IDE (как настраивать, зависит от конкретной IDE), если не нашли, то ищут в
    * путях, прописанных в системных переменных `INCLUDE` (в Windows) или `C_INCLUDE_PATH` (в Linux), если не нашли, то в
    * встроенных путях компилятора.    
* `#include "a.h"` внутри файла `b.c` ищут файл `a.h` в:
    * текущей директории файла `b.c`, если не нашли, то 
    * так же, как для `<>`.

**Заголовочные файлы установленных библиотек пишут обычно с `<>`, а заголовочные файлы самого проекта с `""`.**

## `static` - в пределах одного файла

Я написала функцию для отладочной печати, которую хочу использовать только в своем модуле и никому больше она не будет нужна. Как ее назвать, если в проекте еще много файлов и функции `print` и `print_debug`уже есть? Придется называть `приложение_сервис_модуль_print_debug`, чтобы не было одинаковых названий с аналогичными функциями других модулей?

Мы разбивали проект на модули, чтобы уменьшить связанность между модулями. То есть минимизировать количество функций, которые "торчат наружу" из модуля. Это публичный интерфейс модуля. При этом может быть много функций, которые используют только внутри модуля. Это приватная часть интерфейса модуля. 

Чтобы пометить, что функция может быть вызвана только внутри файла, где она реализована, используют ключевое слово **static**.

**static вне функций и блоков - значит область видимости от момента объявления до конца файла.** 

Есть два файла `main.c` и `helper.c`.
```cpp
// Файл helper.c
#include <stdio.h>

// от этого места до конца файла можно вызывать функцию private_helper
static void private_helper();

// Эту функцию увидят все (и main.c тоже)
void public_function() {
    printf("Я доступна всем!\n");
    private_helper(); // Можно вызвать, потому что мы внутри того же файла
}

// static делает функцию приватной для этого файла
static void private_helper() {
    printf("Только для helper.c\n");
}
```
Функцию `private_helper` можно использовать только внутри 

```cpp
#include <stdio.h>

// Объявляем, что такая функция есть где-то (в другом файле)
void publicFunction();
// мы декларируем какую-то другую функцию, а не private_helper из helper.c, так как там она static
void private_helper();

int main() {
    publicFunction(); // Это РАБОТАЕТ
    
    // privateHelper(); // ОШИБКА! Линковщик не найдет эту функцию,
                         // потому что она static и "спрятана" в helper.c
    return 0;
}
```

## Переменные 

Пусть в файле `a.c` определена глобальная переменная `int x`. 

Глобальная: 

* определена **вне блоков и функций**,
* время жизни равно **времени жизни программы**,
* по умолчанию **инициализируется 0**,
* область видимости - от места определения (definition) до конца файла и в других файлах.

Чтобы переменную увидели в других файлах, нужно сообщить компилятору, что это "чужая" переменная, не надо ждать ее объявления (definition) в этом файле. Чтобы работать с переменной компилятору нужно знать её имя и тип. То есть определение, декларация переменной (declaration) должно содержать:

* информацию, что переменная где-то будет определена, ключевое слово **extern**
* тип переменной,
* идентификатор переменной.

### extern

```cpp
// Файл a.c
int x = 7;      // глобальная переменная: объявление и инициализация
```
Использование этой переменной в другом файле:
```cpp
#include <stdio.h>

extern int x;   // декларация переменной

int main()
{
    printf("x = %d\n", x);  // использование переменной из другого файла
    return 0;
}
```

### Заголовочный файл `a.h`

Декларация переменной с `extern` похожа на прототип функции. И, как и прототип функции, её можно использовать в том же файле, что и определение:

```cpp
// Файл a.h
extern int x;   // обещание, что где-то переменная будет объявлена
int x = 7;      // глобальная переменная: объявление и инициализация
```

Как вы понимаете, если переменная является частью внешнего API, как и функция, то `extern int x;` тоже пишут в заголовочный файл и вставляют везде, где будет нужно это API.

Заголовочный файл:
```cpp
// файл a.h
extern int x;   // обещание, что где-то переменная будет объявлена
```
Использование в другом файле:
```cpp
#include <stdio.h>
#include "a.h"

int main()
{
    printf("x = %d\n", x);  // использование переменной из другого файла
    return 0;
}
```
Не нужно, но можно вставить в тот файл, где переменная объявляется:
```cpp
// Файл a.c
#include "a.h"  // не нужно, но не вызовет ошибку

int x = 7;      // глобальная переменная: объявление и инициализация
```

### Declaration & definition

* Объявление переменной (definition):
    * `int x`;
    * **выделяет память** для хранения переменной.
* Декларация переменной:
    * `extern int x;`
    * память под переменную `x` НЕ выделяется, **обещание компилятору**, что где-то в другом файле переменная объявлена и память под нее выделена.
    
### Декларация без объявления - ошибка

"Обещание компилятору", декларация, не гарантирует, что где-то в коде будет объявление переменной. В этом случае, как и для функции без реализации, происходит ошибка линковки.

**Обещал - не значит женился**.

### Объявление в нескольких местах - ошибка

Декларацию переменной мы можем написать во многих файлах, но объявление её должно быть только в одном месте:

```cpp
// Файл a.c
extern int x;   // можно пообещать, что переменная будет
int x = 7;      // и сделать её!
```
Редактор связей не понимает, какую именно переменную `x` использовать. Он нашел две разных переменных `x`.
```cpp
#include <stdio.h>
extern int x;   // можно пообещать, что переменная будет
int x;          // ОШИБКА, переменная объявлена второй раз

int main()
{
    printf("x = %d\n", x);
    return 0;
}
```

### static - не совсем глобальная переменная

Как называют такую переменную по русски? Статическая? А как отделяют в терминологии от static int k внутри функции?

Так же, как в функциях, если мы хотим объявить переменную вне блоков и функций, но так, чтобы её не было видно в других файлах, объявляем ее как **static**
    
```cpp
// Файл a.c
static int x = 7;      // видна только в этом файле

void foo()
{
    x++;
}
```
В другом файле эту переменную использовать нельзя:
```cpp
// Файл b.c
#include <stdio.h>
extern int x;   // можно пообещать, что переменная будет

int main()
{
    printf("x = %d\n", x);      // Ошибка!
    return 0;
}
```
Линковщик не видит переменной `x` из файла `a.c` и возникает ошибка связывания.

Зато можно в другом файле объявить `static int x;` и это будет другая переменная. Она не имеет никакого отношения к переменной `x` из файла `a.c`: 
```cpp
// Файл c.c

static int x = 12;  // это другая переменная 
```

### Предупреждение

[Почему не стоит использовать глобальные переменные](https://stepik.org/lesson/406095/step/12)

В следующем курсе в проекте мы сделаем много глобальных переменных. Чтобы вы прочувствовали боль отладки программ с такими переменными. Лучше используйте функции для чтения и записи в переменные и делайте их `static`, а не глобальными.

Хороший пример глобальной переменной: `errno`. В нее пишут код ошибки стандартные функции и системные вызовы. Все знают, где искать информацию в случае ошибки вызова функции. 

Ещё вам известны глобальные переменные `stdin`, `stdout`, `stderr`. Потому что у каждой программы есть по умолчанию три потока данных. Все знают их имена.
    
## Типы и макросы

**Везде и всюду** - пишем в заголовочных файлах и вставляем везде, где нужно.

Почему так сделано? 

* Если надо декларировать массив, а его длина задана в макросе, то везде, где пишем декларацию, надо писать размер массива, то есть макрос.
* Если в прототипе функции или декларации переменной используется нестандартный тип, то информацию о нем нужно написать везде перед прототипом функции или декларацией переменной.

### Пример макроса

```cpp
// Файл a.h

#define N 10

extern int a[N];
```    
Использование в `.c` файлах:

```cpp
// Файл a.c
#include "a.h"

int a[N];                       // используем N при объявлении переменной

void fill_one()
{
    for(int i = 0; i < N; i++)  // используем N в цикле
        a[i] = 1;
}
```

### Пример typedef и struct

В этом файле определяем что такое `ull` и что такое `Decimal`:

```cpp
// Файл decimal.h

// псевдоним для определения больших чисел
typedef unsigned long long ull;

// структура для хранения еще больших чисел
struct Decimal {
    char * a;       // a[0]*10^0 + a[1]*10^1 + a[2]*10^2 + ...
    int n;          // максимальная степень 10
    int size;       // размер динамического массива a
}

Decimal * elong_set_int(ull value);             // преобразует value в тип Decimal
Decimal * elong_set_str(char * str);            // преобразует str в тип Decimal
void      elong_destroy(Decimal * value);       // освобождение памяти
void      elong_print(Decimal * value);         // печать числа
Decimal * elong_add(Decimal * a, Decimal * b);  // return a + b
```
Можно использовать эти типы после вставки заголовочного файла:

```cpp
// Файл main.c

#include "decimal.h"

int main()
{
    Decimal * first = elong_set_int(1234567890UL);
    Decimal * second = elong_set_str("12345678901234567890");
    
    Decimal * res = elong_add(first + second);
    
    elong_print(first);
    elong_print(second);
    elong_print(res);
    
    elong_destroy(first);
    elong_destroy(second);
    elong_destroy(res);
    
    return 0;
}
```

## Что нужно и что нельзя писать в заголовочный файл

* В заголовочный файл:
    * макросы: `#define`,
    * новые типы и алиасы: `typedef` + `struct`,
    * прототипы функций,
    * декларации переменных `extern`,
    * можно вставить другие заголовочные файлы.

Компилятор и линкер разрешает в заголовочных файлах писать любые синтаксически корректные конструкции.

Некоторые конструкции должны быть в программе в единственном экземпляре. Принято их не писать в заголовочном файле. Иначе мы вставим `my_header.h` в файлы `a.c` и `b.c`, и получим ошибку. Программист не должен помнить, что какой-то файл в программе можно вставлять только один раз.

Что не следует вставлять в заголовочные файлы? **Все, что приводит к выделению памяти в программе**:

* объявление переменных,
* реализация функций.

### В заголовочном файле `.h`

```cpp
// файл stack.h

// макрос
#define N 100           

// типы и алиасы
typedef int Data;
struct Stack {
    Data a[N];
    int n;
};
typedef struct Stack Stack;

// декларации переменных (так определены в stdio.h)
extern FILE * stdin;
extern FILE * stdout;
extern FILE * stderr;

// прототипы функций
void stack_init(Stack * stack);
```

### `.c` файл

Все, что можно написать в `.h` файле, можно написать в `.c` файле.

```cpp
// файл stack.c
#include "stack.h"

// нельзя написать в .h файле, только в .c файле:

// объявление переменных
// ускорение свободного падения на планете, по умолчанию на Земле
double planet_gravity_coefficient = 9.8;

// реализация функций
void stack_init(Stack * stack)
{
    stack->n = 0;
}
```

### Последнее предупреждение

*Внимание! Кто на зачете напишет `#include a.c` (вставит не `.h` файл, а `.c` файл) или напишет ересь в заголовочный файл, получит неуд в зачетку!*
