## Программа в виде проекта


До этого момента мы писали все программы в одном-единственном файле. Пока программа была маленькой, это было нормально. Но как только код переваливал за сотню строк, начинались неудобства:  

* долго искать, где находится нужная функция,  
* непонятно, где заканчивается одна логическая часть и начинается другая,  
* страшно что-то менять — вдруг сломаешь что-то в другом месте,
* несколько человек не могут одновременно работать над кодом.

Поэтому в реальных проектах код почти никогда не держат в одном файле. Программу разбивают на несколько файлов, а часто ещё и раскладывают эти файлы по папкам. Получается структура, которую принято называть **модульной**.

Представьте, что мы пишем [калькулятор на основе стека](https://stepik.org/lesson/657369/step/2). Удобнее разделить программу на файлы:

* `stack.c` — реализация функций работы со стеком,
* `calculator.c` — логика самого калькулятора (разбор выражений, приоритеты операций, вызов функций стека)  
* `main.c` — только запуск программы, чтение ввода и вызов калькулятора.

Когда проект становится большим (сотни, тысячи, а иногда и десятки тысяч файлов), такое разделение — уже не удобство, а необходимость.

### Главные преимущества модульного подхода

* **Принцип «чёрного ящика»** 
Один программист (или команда) пишет реализацию стека и говорит остальным через прототипы функций и их описание: «Вот вам эти функции, пользуйтесь ими вот так». И всё. Остальным не нужно знать, лежит ли внутри стека обычный массив, динамический массив, односвязный список и т.п. Они видят только интерфейс и работают через него. В уроке мы расскажем как лучше оформлять интерфейс (прототипы функций и глобальные переменные) в отдельном файле, который называется **заголовочный файл** и имеет расширение `.h`

* **Локальность ошибок и отладки** 
Если в калькуляторе неправильно работает вычитание, то сразу понятно, что проблема почти наверняка не в функциях push/pop.
Можно отдельно протестировать стек и убедиться, что он ведёт себя правильно. Тогда остаётся смотреть только логику калькулятора.

* **Лёгкая замена модуля**
Допустим, сначала мы сделали стек на статическом массиве размером 32 элемента. Потом оказалось, что этого мало. Мы спокойно переписываем только `stack.c` и `stack.h` (переходим на динамический массив или на связный список), а весь остальной код — калькулятор, main, чтение и разбор входной строки — даже не замечает этой замены. Главное, чтобы сигнатуры функций остались прежними.

* **Удобство навигации по коду**
Как в шкафу: носки — в одном ящике, футболки — в другом, брюки — на отдельной полке.
Когда стек в отдельном файле (а лучше ещё и в папке `structures/stack/`), его легко найти.

### Что нужно изучить

Чтобы разбивать код на модули, нам предстоит разобраться с четырьмя вещами:

* **Сборка**. Как скомпилировать много `.c` файлов в одну программу.
* **Импорт**. Как в одном файле использовать из другого:
    * функции,
    * переменные,
    * макросы,
    * структуры и типы (`typedef`).
* **Сокрытие**. Как сделать так, чтобы функция или переменная были не видны снаружи. Это нужно, чтобы в разных модулях могли быть свои функции с одинаковыми именами — и они не конфликтовали.
* **Заголовочные файлы**. Что писать в `.h` файлах и как правильно их подключать, чтобы всё работало.

Всё это разберём по порядку.

## Компиляция и сборка проекта

Если программа состоит из файлов `a.c` и `b.c`, а исполняемый модуль `hello.exe`, то<br/> **для компиляции и сборки нужных `.c` файлов просто перечислите их через пробел**:

```cpp
gcc -Wall -Wextra -g a.c b.c -o hello.exe
```

### Для ленивых

Компиляция всех `.c` файлов в текущей директории, сборка в исполняемый модуль по умолчанию (`a.exe` или `a.out`):
```cpp
gcc -Wall -Wextra -g *.c
```

### Для любознательных

Используйте [make-файл](https://stepik.org/lesson/512586?unit=504796). О нем лучше прочитать в конце этого урока, когда вы поймете, что такое `.h` файлы и зачем они нужны.

*Очень нужны, когда в проекте полная сборка проекта с компиляцией всех файлов занимает несколько часов. И хочется, исправив несколько файлов, не ждать полной пересборки, а быстро перекомпилировать измененные файлы и собрать исполняемый модуль.*

### Разделение этапа компиляции файлов и сборки

Можно разделить компиляцию в объектные файлы `a.o` и `b.o` и их сборку [компановщиком](https://stepik.org/lesson/562180/step/4) (редактором связей, линкером, linker) в исполняемый модуль `hello.exe`:

* `gcc -c a.c` - скомпилировали файл `a.c` в объектный файл `a.o`.
* `gcc -c b.c` - скомпилировали файл `b.c` в объектный файл `b.o`.
* `gcc a.o b.o -o hello.exe` - собрали объектные файлы `a.o` и `b.o` в исполняемый модуль `hello.exe`.

## Вызов функции из другого файла

Начнём с самого простого случая — с функций. Допустим, мы реализовали какую-то полезную функцию в одном файле, а вызывать её хотим в другом. Как это сделать?

Достаточно написать её **прототип** в том файле, где мы собираемся её вызывать. Компилятору этого хватит.

### Разбираем на примере

Пусть у нас есть файл `a.c`, в котором реализована функция `foo`. И она нам понадобилась в двух местах: в том же `a.c` (в другой функции) и в файле `b.c`.

Файл `a.c`, где реализована функция `foo`:
```cpp
// Файл a.c
#include <stdio.h>

void foo(int x);    // прототип функции

void bzz()
{
    foo(17);        // вызываем foo — без прототипа выше не сработало бы
}

void foo(int x)     // реализация функции
{
    printf("a.c foo: x=%d\n", x);
}
```
Файл `b.c`, где вызывается функция `foo`:
```cpp
// Файл b.c

void foo(int x);    // опять прототип — теперь для другого файла

int main()
{
    foo(7);         // вызываем foo, которая реализована в a.c
    return 0;
}
```

Оба файла компилируются без ошибок. Почему? Потому что прототип — это как обещание компилятору: «не волнуйся, функция foo где-то есть, вот как она выглядит, можешь проверять типы аргументов и возвращаемого значения и готовить код вызова». А где конкретно лежит реализация — в этом же файле или в соседнем, разберётся уже сборщик (линковщик) на финальном этапе.

### Что будет, если функции нет?

Тут возможны три ситуации, и их полезно различать.

#### Ситуация 1. Функция объявлена (есть прототип), но нигде не вызывается.

```cpp
// Файл b.c

void foo(int x);                      // прототип
void not_implemented_yet_function();  // ещё один прототип

int main()
{
    foo(7);          // эта вызывается
    // а вторую не вызываем
    return 0;
}
```
Ошибки не будет. Функция `not_implemented_yet_function` просто висит как обещание, но раз её никто не требует — компилятор и сборщик на это не жалуются. Так бывает, например, когда вы заготовили функцию на будущее, но пока не используете.

#### Ситуация 2. Функция вызывается, еще не реализована и прототипа нет.

Это классическая опечатка в имени. Компилятор встречает вызов `fooqqq(7)`, но понятия не имеет, что это за функция. Он выдаст ошибку компиляции примерно такого толка: «'fooqqq' is not declared». Или `implicit declaration of function`, потому что считает первый вызов функции ее неявной декларацией со всеми аргументами типа `int`. С этим вы наверняка уже сталкивались.

#### Ситуация 3. Прототип есть, функция вызывается, но нигде не реализована.

Вот это самый интересный случай:

```cpp
// Файл b.c

void foo(int x);            // прототип есть
void unknown_function();    // и на эту тоже есть прототип

int main()
{
    foo(7);                 // эта функция есть в a.c, всё хорошо
    unknown_function();     // а этой — нет нигде

    return 0;
}
```
Попробуем скомпилировать по отдельности:

```bash
gcc -c b.c   # создаст b.o — компиляция пройдёт успешно!
```
Файл `b.o` благополучно создастся. Компилятор увидел прототипы, проверил, что типы аргументов совпадают, и успокоился. Его дело — превратить код в машинные инструкции, а где лежат недостающие куски — он не проверяет.

А вот когда мы попытаемся собрать всё вместе:

```bash
gcc -o hello.exe a.o b.o
```
вот тут линковщик (эта программа, которая собирает объектные файлы воедино) полезет искать реализацию `unknown_function` и не найдёт:

```
/usr/bin/ld: b.o: in function `main':
b.c:(.text+0x18): undefined reference to `unknown_function'
collect2: error: ld returned 1 exit status
```
Это и есть ошибка сборки (линковки). Файлы скомпилировались, а собраться в работающую программу не смогли. Кто-то не выполнил своё обещание.

## Заголовочные файлы: избавляемся от дублирования

Мы научились вызывать функции из других файлов, просто написав их прототип в нужном месте. 

Допустим, у нас есть функция, которая используется в десятке разных файлов. В каждом из этих файлов мы  написали её прототип. Но вдруг потребовалось изменить функцию: например изменить тип одного из параметров с `char` на `int`.

Что делать? Правильно, надо полезть во все эти десять файлов и в каждом исправить прототип. А если их двадцать? А если через полгода мы вообще забудем, в каких именно файлах эта функция вызывается? Один файл пропустили — и всё, программа не соберётся, а ошибка будет выглядеть так, будто функция вообще не существует.

Хочется же, чтобы нужно было исправлять в двух местах: в самой реализации и в одном-единственном месте с прототипом. А чтобы во все остальные файлы это изменение подтянулось само.

И такая возможность есть.

### Подключаем файлы с помощью `#include`

Идея простая: выносим все прототипы функций, которые должны быть видны снаружи, например, файла `stack.c`, в отдельный файл `stack.h`. А потом вставляем этот файл во все места, где нужны эти прототипы, с помощью команды препроцессора `#include`. Препроцессор берёт содержимое указанного файла и подставляет его вместо строчки с `#include` — как будто вы сами скопировали и вставили.

Такие файлы называют **заголовочными**, и по сложившейся традиции им дают расширение `.h` (от header).

### Переделываем наш пример

Вернёмся к примеру с файлами `a.c` и `b.c`. Добавим к ним третий — заголовочный файл `a.h`.

Создаём файл `a.h` и кладём в него прототип функции:

```cpp
// Файл a.h
void foo(int x);
```

Теперь подключаем этот заголовочный файл в `a.c` — туда, где функция реализована:

```cpp
// Файл a.c
#include <stdio.h>
#include "a.h"      // вставили содержимое a.h

void bzz()
{
    foo(17);        // вызываем foo, прототип теперь из a.h
}

void foo(int x)     // сама реализация
{
    printf("a.c foo: x=%d\n", x);
}
```
И точно так же подключаем `a.h` в `b.c`, где функция вызывается:

```cpp
// Файл b.c
#include "a.h"      // и сюда вставили

int main()
{
    foo(7);
    return 0;
}
```
Теперь, если мы захотим изменить тип параметра у `foo`, мы исправим прототип ровно в одном месте — в файле `a.h`. И в `a.c`, и в `b.c` изменения придут автоматически через `#include`.

### `stdio.h`

Вы наверняка замечали, что мы с самого начала пишем `#include <stdio.h>`, чтобы пользоваться `printf` и `scanf`. 

`stdio.h` — это точно такой же заголовочный файл. Его написали за нас разработчики стандартной библиотеки. Там лежат прототипы всех функций для работы с вводом-выводом. Мы их вызываем, компилятор проверяет типы по прототипам, а реализации (уже скомпилированные) лежат в библиотеках и подключаются на этапе сборки.

### Угловые скобки vs кавычки

Обратите внимание, как именно мы подключаем файлы:

```cpp
#include <stdio.h>   // угловые скобки
#include "a.h"       // кавычки
```
Разница между `<>` и `""` в том, где будут искать указанные файлы.

* `#include <stdio.h>` - ищи файл `stdio.h` в:
    * include-директориях, которые заданы через ключ `-I` в `gcc` или в IDE (как настраивать, зависит от конкретной IDE), если не нашли, то ищи в
    * путях, прописанных в системных переменных `INCLUDE` (в Windows) или `C_INCLUDE_PATH` (в Linux), если не нашли, то ищи в
    * встроенных путях компилятора.
    Так подключают стандартные библиотеки и вообще всё, что не является частью вашего проекта.
* `#include "a.h"` внутри файла `b.c` - ищи файл `a.h` в:
    * текущей директории файла `b.c`, если не нашли, то 
    * ищи так же, как для `<>`.
    Так подключают заголовочные файлы проекта.

**Заголовочные файлы установленных библиотек пишут обычно с `<>`, а заголовочные файлы самого проекта с `""`.**

Юра, корректно заменить на фразу ниже?

Поэтому простое правило: **системные заголовки — в `<>`, свои — в `""`**.

## Ключевое слово static: прячем функции внутри файла

Представьте ситуацию. Я пишу свой модуль и в процессе разработки создаю вспомогательную функцию, например, для отладочной печати. Нужна она только внутри моего модуля, наружу я её отдавать не планирую — другим модулям эта функция ни к чему, они будут работать только с публичным интерфейсом.

Вопрос: как её назвать? В проекте уже есть куча файлов, и наверняка в каком-нибудь другом модуле кто-то тоже захотел назвать свою служебную функцию `print_debug`. Если я назову свою так же, при сборке возникнет конфликт — линковщик не поймёт, какую именно `print_debug` вызывать, если они обе видны глобально.

Можно, конечно, придумывать длинные имена вроде `мой_модуль_внутренняя_print_debug`. Но это не читаемо и не удобно. Зачем выдумывать костыли, если в языке есть нормальное решение?

Вспомним, зачем мы вообще разбивали программу на модули. Мы хотели уменьшить связанность между ними, оставив снаружи только минимум необходимых функций — публичный интерфейс (API). А всё, что используется только внутри модуля, должно быть спрятано, чтобы случайно не пересечься с такими же внутренними функциями из других модулей.

Для этого в C есть ключевое слово **static**.

### Как это работает

Если написать `static` перед функцией (или глобальной переменной), то она будет видна **только в пределах того файла, где объявлена**. Для всех остальных файлов она как будто не существует. Линковщик про неё ничего не знает, и конфликтов имён не возникает.

*В языке Си нет терминов приватная и публичная функция, как в C++. Но по сути функции со `static` работают как приватные, только внутри данного файла. А все остальные - как публичные, могут быть доступны во всем проекте.*

### Смотрим на примере

Пусть у нас есть два файла: `helper.c` и `main.c`.

#### Файл `helper.c`:

```cpp
#include <stdio.h>

// Объявляем приватную функцию (пока без реализации)
static void private_helper();

// Публичная функция — доступна всем
void public_function() {
    printf("Я доступна всем!\n");
    private_helper(); // внутри файла вызывать можно
}

// Реализация приватной функции
static void private_helper() {
    printf("Только для helper.c\n");
}
```
Что тут произошло? Функция `private_helper` помечена `static`. Это значит, что она существует только внутри `helper.c`. Из других файлов к ней не обратиться — линковщик просто не найдёт её при сборке.

#### Файл `main.c`:

```cpp
#include <stdio.h>

// Объявляем, что функция public_function живёт где-то в другом файле
void public_function();

// А вот так делать бессмысленно:
// void private_helper(); // Эту функцию всё равно не вызвать — она static в helper.c

int main() {
    public_function();   // РАБОТАЕТ — функция публичная и доступна

    // private_helper(); // ОШИБКА! Линковщик скажет: undefined reference
                         // Функция private_helper есть, но она static и скрыта в helper.c

    return 0;
}
```

### Запомните

* `static` у функции (или глобальной переменной) означает: «это моё личное, чужим не давать».
* Такая функция видна только внутри своего файла, **начиная с места объявления и до конца файла**.
* В других файлах можно спокойно создавать свои `static`-функции с теми же именами — конфликта не будет.
* Это идеальный инструмент для реализации внутренних «подсобных» функций модуля, которые не должны торчать наружу.

Так что никаких длинных префиксов и ручного отслеживания уникальности имён. Просто пишем `static` — и живём спокойно.

### Длинные идентификаторы

Помните поговорку "что русскому здорово, то немцу смерть"? Верно и обратное. ## `static` - в пределах одного файла

Я написала функцию для отладочной печати, которую хочу использовать только в своем модуле и никому больше она не будет нужна. Как ее назвать, если в проекте еще много файлов и функции `print` и `print_debug`уже есть? Придется называть `приложение_сервис_модуль_print_debug`, чтобы не было одинаковых названий с аналогичными функциями других модулей?

Мы разбивали проект на модули, чтобы уменьшить связанность между модулями. То есть минимизировать количество функций, которые "торчат наружу" из модуля. Это публичный интерфейс модуля. При этом может быть много функций, которые используют только внутри модуля. Это приватная часть интерфейса модуля. 

Чтобы пометить, что функция может быть вызвана только внутри файла, где она реализована, используют ключевое слово **static**.

**static вне функций и блоков - значит область видимости от момента объявления до конца файла.** 

Есть два файла `main.c` и `helper.c`.
```cpp
// Файл helper.c
#include <stdio.h>

// от этого места до конца файла можно вызывать функцию private_helper
static void private_helper();

// Эту функцию увидят все (и main.c тоже)
void public_function() {
    printf("Я доступна всем!\n");
    private_helper(); // Можно вызвать, потому что мы внутри того же файла
}

// static делает функцию приватной для этого файла
static void private_helper() {
    printf("Только для helper.c\n");
}
```
Функцию `private_helper` можно использовать только внутри 

```cpp
#include <stdio.h>

// Объявляем, что такая функция есть где-то (в другом файле)
void publicFunction();
// мы декларируем какую-то другую функцию, а не private_helper из helper.c, так как там она static
void private_helper();

int main() {
    publicFunction(); // Это РАБОТАЕТ
    
    // privateHelper(); // ОШИБКА! Линковщик не найдет эту функцию,
                         // потому что она static и "спрятана" в helper.c
    return 0;
}
```

## Переменные 

Пусть в файле `a.c` определена переменная `x`. 

```cpp
int x = 7;
```

Это **глобальная** переменная: 

* Определена **вне блоков и функций**
* **Время жизни** — она создаётся в момент запуска программы и живёт до самого её завершения
* **Инициализируется** нулями — если мы явно не присвоим ей значение (например, напишем просто `int x;`), компилятор по умолчанию положит туда `0`,
* **Область видимости** — по умолчанию она видна от места своего определения до конца файла. Но есть нюанс: если очень захотеть, её можно «увидеть» и в других файлах. Для этого существует специальное ключевое слово **extern**. Разберемся, как это работает.

Чтобы переменную увидели в других файлах, нужно сообщить компилятору, что эта переменная может быть **объявлена** (**definition**) в другом файле. Чтобы работать с переменной компилятору нужно знать её имя и тип. То есть **определение**, декларация переменной (**declaration**) должно содержать:

* ключевое слово **extern** - информацию, что переменная где-то будет определена, 
* **тип** переменной,
* **идентификатор** - имя переменной.

### extern

```cpp
// Файл a.c
int x = 7;      // объявление переменной (definition): память выделена, значение задано
```
Использование этой переменной в другом файле `b.c`:
```cpp
// Файл b.c
#include <stdio.h>

extern int x;   // декларация переменной (declaration): "где-то есть переменная х типа int"

int main()
{
    printf("x = %d\n", x);  // использование переменной из другого файла
    return 0;
}
```

Внимание: В `b.c` мы **не** пишем `extern int x = 7;`, только `extern` + тип + имя. 

Здесь не выделяется память для переменной `x`, поэтому *некуда* сохранить число `7`. Никаких инициализаций! Только обещание компилятору, что переменная с этим именем и типом будет где-то объявлена.

### Заголовочный файл `a.h`

Декларация переменной с `extern` похожа на прототип функции. И, как и прототип функции, её можно использовать в том же файле, что и определение:

```cpp
// Файл a.h
extern int x;   // обещание, что где-то переменная будет объявлена
int x = 7;      // глобальная переменная: объявление и инициализация
```

Как вы понимаете, если переменная является частью внешнего API, как и функция, то `extern int x;` тоже пишут в заголовочный файл и вставляют везде, где будет нужно это API.

Заголовочный файл:
```cpp
// файл a.h
extern int x;   // обещание, что где-то переменная будет объявлена
```
Использование в другом файле:
```cpp
#include <stdio.h>
#include "a.h"

int main()
{
    printf("x = %d\n", x);  // использование переменной из другого файла
    return 0;
}
```
Не нужно, но можно вставить в тот файл, где переменная объявляется:
```cpp
// Файл a.c
#include "a.h"  // не нужно, но не вызовет ошибку

int x = 7;      // глобальная переменная: объявление и инициализация
```

### Declaration & definition

* Объявление переменной (definition):
    * `int x`;
    * **выделяет память** для хранения переменной.
* Декларация переменной:
    * `extern int x;`
    * память под переменную `x` НЕ выделяется, **обещание компилятору**, что где-то в другом файле переменная объявлена и память под нее выделена.
    
### Декларация без объявления - ошибка

"Обещание компилятору", декларация, не гарантирует, что где-то в коде будет объявление переменной. В этом случае, как и для функции без реализации, происходит ошибка линковки.

**Обещал - не значит женился**.

### Объявление в нескольких местах - ошибка

Декларацию переменной мы можем написать во многих файлах, но объявление её должно быть только в одном месте:

```cpp
// Файл a.c
extern int x;   // можно пообещать, что переменная будет
int x = 7;      // и сделать её!
```
Редактор связей не понимает, какую именно переменную `x` использовать. Он нашел две разных переменных `x`.
```cpp
#include <stdio.h>
extern int x;   // можно пообещать, что переменная будет
int x;          // ОШИБКА, переменная объявлена второй раз

int main()
{
    printf("x = %d\n", x);
    return 0;
}
```

### static - не совсем глобальная переменная

Как называют такую переменную по русски? Статическая? А как отделяют в терминологии от static int k внутри функции?

Так же, как в функциях, если мы хотим объявить переменную вне блоков и функций, но так, чтобы её не было видно в других файлах, объявляем ее как **static**
    
```cpp
// Файл a.c
static int x = 7;      // видна только в этом файле

void foo()
{
    x++;
}
```
В другом файле эту переменную использовать нельзя:
```cpp
// Файл b.c
#include <stdio.h>
extern int x;   // можно пообещать, что переменная будет

int main()
{
    printf("x = %d\n", x);      // Ошибка!
    return 0;
}
```
Линковщик не видит переменной `x` из файла `a.c` и возникает ошибка связывания.

Зато можно в другом файле объявить `static int x;` и это будет другая переменная. Она не имеет никакого отношения к переменной `x` из файла `a.c`: 
```cpp
// Файл c.c

static int x = 12;  // это другая переменная 
```

### Предупреждение

[Почему не стоит использовать глобальные переменные](https://stepik.org/lesson/406095/step/12)

В следующем курсе в проекте мы сделаем много глобальных переменных. Чтобы вы прочувствовали боль отладки программ с такими переменными. Лучше используйте функции для чтения и записи в переменные и делайте их `static`, а не глобальными.

Хороший пример глобальной переменной: `errno`. В нее пишут код ошибки стандартные функции и системные вызовы. Все знают, где искать информацию в случае ошибки вызова функции. 

Ещё вам известны глобальные переменные `stdin`, `stdout`, `stderr`. Потому что у каждой программы есть по умолчанию три потока данных. Все знают их имена.
    
## Типы и макросы

**Везде и всюду** - пишем в заголовочных файлах и вставляем везде, где нужно.

Почему так сделано? 

* Если надо декларировать массив, а его длина задана в макросе, то везде, где пишем декларацию, надо писать размер массива, то есть макрос.
* Если в прототипе функции или декларации переменной используется нестандартный тип, то информацию о нем нужно написать везде перед прототипом функции или декларацией переменной.

### Пример макроса

```cpp
// Файл a.h

#define N 10

extern int a[N];
```    
Использование в `.c` файлах:

```cpp
// Файл a.c
#include "a.h"

int a[N];                       // используем N при объявлении переменной

void fill_one()
{
    for(int i = 0; i < N; i++)  // используем N в цикле
        a[i] = 1;
}
```

### Пример typedef и struct

В этом файле определяем что такое `ull` и что такое `Decimal`:

```cpp
// Файл decimal.h

// псевдоним для определения больших чисел
typedef unsigned long long ull;

// структура для хранения еще больших чисел
struct Decimal {
    char * a;       // a[0]*10^0 + a[1]*10^1 + a[2]*10^2 + ...
    int n;          // максимальная степень 10
    int size;       // размер динамического массива a
}

Decimal * elong_set_int(ull value);             // преобразует value в тип Decimal
Decimal * elong_set_str(char * str);            // преобразует str в тип Decimal
void      elong_destroy(Decimal * value);       // освобождение памяти
void      elong_print(Decimal * value);         // печать числа
Decimal * elong_add(Decimal * a, Decimal * b);  // return a + b
```
Можно использовать эти типы после вставки заголовочного файла:

```cpp
// Файл main.c

#include "decimal.h"

int main()
{
    Decimal * first = elong_set_int(1234567890UL);
    Decimal * second = elong_set_str("12345678901234567890");
    
    Decimal * res = elong_add(first + second);
    
    elong_print(first);
    elong_print(second);
    elong_print(res);
    
    elong_destroy(first);
    elong_destroy(second);
    elong_destroy(res);
    
    return 0;
}
```

## Что нужно и что нельзя писать в заголовочный файл

* В заголовочный файл:
    * макросы: `#define`,
    * новые типы и алиасы: `typedef` + `struct`,
    * прототипы функций,
    * декларации переменных `extern`,
    * можно вставить другие заголовочные файлы.

Компилятор и линкер разрешает в заголовочных файлах писать любые синтаксически корректные конструкции.

Некоторые конструкции должны быть в программе в единственном экземпляре. Принято их не писать в заголовочном файле. Иначе мы вставим `my_header.h` в файлы `a.c` и `b.c`, и получим ошибку. Программист не должен помнить, что какой-то файл в программе можно вставлять только один раз.

Что не следует вставлять в заголовочные файлы? **Все, что приводит к выделению памяти в программе**:

* объявление переменных,
* реализация функций.

### В заголовочном файле `.h`

```cpp
// файл stack.h

// макрос
#define N 100           

// типы и алиасы
typedef int Data;
struct Stack {
    Data a[N];
    int n;
};
typedef struct Stack Stack;

// декларации переменных (так определены в stdio.h)
extern FILE * stdin;
extern FILE * stdout;
extern FILE * stderr;

// прототипы функций
void stack_init(Stack * stack);
```

### `.c` файл

Все, что можно написать в `.h` файле, можно написать в `.c` файле.

```cpp
// файл stack.c
#include "stack.h"

// нельзя написать в .h файле, только в .c файле:

// объявление переменных
// ускорение свободного падения на планете, по умолчанию на Земле
double planet_gravity_coefficient = 9.8;

// реализация функций
void stack_init(Stack * stack)
{
    stack->n = 0;
}
```

### Последнее предупреждение

*Внимание! Кто на зачете напишет `#include a.c` (вставит не `.h` файл, а `.c` файл) или напишет ересь в заголовочный файл, получит неуд в зачетку!*
